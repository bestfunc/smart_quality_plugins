# 10 · 版本线与交付

> 事实来源:git 分支命名(`feature/v3.x`、现场专版分支)、git tag 命名(`release-YYMMDD`、现场专版 tag)、代码内版本号字符串(`BestPLC/MainWindow.xaml` 标题栏)及其 git 历史。商业模式部分无可靠依据,标 `<TODO>`。

## 一句话

SmartPLC 走**多版本并存**路线:不同现场可以跑不同主版本;版本号写在程序标题栏,用**主次号 + 日期戳**标识;发版以**日期戳 git tag**为锚,约 2-3 周一个大版本;不同现场可出**专版分支 / 专 tag**;交付形态是**现场单机部署,按点位表配置上线**。

## 版本线策略

多条 `feature/v3.x` 分支长期并存,目的是**同时支撑不同阶段、不同现场的产线**——老现场要稳定、新现场要新能力,不强求所有现场升到同一版本。

| 版本线 | 分支 | 大致定位(据分支活跃度推断) |
|---|---|---|
| **v3.2** | `feature/v3.2`、`feature/v3.2_update` | 较早的稳定线,维护 / 现场专版基线 |
| **v3.3** | `feature/v3.3` | 过渡线 |
| **v3.5** | `feature/v3.5` | 当前开发主线(本仓库当前分支) |
| 更早(v3.0/v3.1) | `feature/v3.0`、`feature/v3.1` | 历史线,仅作参考 |

> 各版本线的"维护 / 开发"定位据分支与提交活跃度推断,非正式发布矩阵;现场实际跑哪一版以交付记录为准。`master` 为发布主干,日期戳 tag 多打在其上。

## 版本号方案

版本号直接写在主窗体标题栏(`BestPLC/MainWindow.xaml`,`Title="SmartPLC - 巅峰表现 <版本号>"`),现场肉眼即可读到当前版本。**格式随版本线演进、并不完全统一**,从 git 历史可见这条演变链:

| 时间(据 git 历史) | 标题栏版本号(实证) | 形态拆解 |
|---|---|---|
| 早期 | `V250310` → `V250331` | 纯日期戳 `VYYMMDD` |
| — | `V250611<现场短码>` | 日期戳 + 现场后缀(脱敏) |
| — | `V3.2.251224` | `V主.次.YYMMDD` |
| — | `v3.3-20260401` | `v主.次-YYYYMMDD`(8 位完整年份) |
| 当前(v3.5) | `V3.520260526.1` | `V主.次` + `YYYYMMDD` + `.patch` |

读法(以当前 `V3.520260526.1` 为例):

```
V 3.5 20260526 .1
  └┬┘ └───┬──┘ └┬┘
 主次号  构建日期  当日补丁序号
        (YYYYMMDD)  (同日多次出版 .1/.2…)
```

要点:

- **主次号**(如 `3.5`)对应版本线;**日期戳**标识构建那天;**patch 序号**用于同一天多次出版(紧急修复)。
- **日期戳位数不统一**:早期 6 位 `YYMMDD`,近期 8 位 `YYYYMMDD`;分隔符也有 `.` / `-` / 直接连写几种写法。引用时**以标题栏实际字符串为准**,不要自己拼。
- 程序内另有 .NET 程序集版本(`Assembly.GetName().Version`,见 `SettingsPage.xaml.cs` / `ErrorContext.cs`),与标题栏的"对外版本号"是两套东西,不要混用。

## 发版与 git tag 节奏

发版以 **日期戳 tag** 为锚,命名 `release-YYMMDD`:

| tag(实证) | 含义 |
|---|---|
| `release-250331` | 2025-03-31 版本 |
| `release-250721` | 2025-07-21 版本 |
| `release-250722` / `release-250722-2` | 同日两个版本,`-2` 为当日第二版(紧急修复 / 重新出版) |
| `release-250802` | 2025-08-02 版本 |

规律:

- **命名锚点是日期**,不是语义版本号——便于现场与 git 对账"这台机器装的是哪天的版本"。
- **同日多版**用 `-2`(以及标题栏 patch 的 `.1/.2`)区分,对应"当天发现问题、当天再出一版"的紧急修复节奏。
- 大版本**节奏约 2-3 周一个**(据 tag 与分支提交间隔的粗略观察,非固定承诺;紧急修复可在任意日加塞)。

## 客户专版机制

系统支持**按现场出专版**——同一套代码基线,针对特定现场的 PLC 点位、协议、流程差异拉出独立分支 / 独立 tag 维护,与主线解耦。从命名约定可见这一机制存在:

| 形态 | 命名约定(实证,已脱敏) | 说明 |
|---|---|---|
| 专版**分支** | `feature/<现场标签>-<日期>`、`<现场标签>-v<n>` | 为某现场拉的独立开发线 |
| 专版 **tag** | `<现场标签>_plc_YYMMDD` | 为某现场打的发布快照 |
| 标题栏**后缀** | `V<日期戳><现场标签>` | 版本号尾部带现场短码,肉眼区分专版 |

机制要点:

- 专版从某条 `feature/v3.x` 基线**分叉**,只承载该现场的差异(点位表、协议组合、特殊流程),不污染主线。
- 专版同样走"标题栏版本号 + 日期戳 tag"的标识方式,只是带现场短码后缀。
- 主线通用能力可回流 / 下发到专版,专版的现场特化一般**不回主线**。

> 本节只描述**机制**。具体现场标签、客户名一律不写入本知识库(见维护说明的裁剪红线)。引用专版时用"某现场专版"指代即可。

## 交付形态

| 维度 | 形态 |
|---|---|
| **部署单元** | 产线现场**单机**:一个 WPF/.NET 8 应用跑在产线工控机(Windows),无容器化 |
| **一机覆盖** | 一台中控连本线 PLC + 录音盒子 + 后端 MySQL / MinIO / 算法服务(见 [02-architecture.md](./02-architecture.md)) |
| **上线方式** | 部署程序 → **按现场点位表配置**(工位 / 设备地址 / 点位映射 / 灵敏度)→ 联调盒子 + 算法 → 投产 |
| **配置载体** | `Settings`(连接串 / 开关)+ 数据库内的工位 / 检测点 / 设备元数据,详见 [08-deployment-config.md](./08-deployment-config.md) |
| **版本识别** | 现场看标题栏版本号即可对账;运维 / 实施按该字符串回查 git tag |

典型上线动作清单见 [scenarios/01-line-operator-setup.md](../scenarios/01-line-operator-setup.md);现场对接客户 PLC 的实战流程见 [scenarios/03-field-implementation.md](../scenarios/03-field-implementation.md)。
