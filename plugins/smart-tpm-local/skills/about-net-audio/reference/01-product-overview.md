# 产品定位与全景

## 一句话定位

**net_audio 是一套部署在产线现场、长时连续采集多通道音频，并以"按时间窗口精准回放"的方式把音频字节流交付给上游算法的嵌入式录音系统。**

它**不是**一个消费级录音机，**也不是**一个会自带 AI 推理的边缘智能盒子；它是上游算法的"音频前端"。

## 它解决的问题

工业产线 / 设备健康监测 / 异常声音检测类的算法应用，长期面临三个工程化痛点：

1. **算法只关心几秒钟的"事件音频"**，但拿不到。声音是瞬时发生的，算法侧拿到信号的时候，那段音频已经过去了。
2. **多麦克风采集 + 时钟同步麻烦**。4 个麦克风采集到的样本必须在同一时间轴上对齐，单机用 ALSA / PortAudio 可以解决，多机就要做时间协议。
3. **算法迭代远快于硬件迭代**。算法侧每月可能要换模型，但硬件采集端不可能跟着改。

net_audio 把这三件事吃下来：
- 后台 **24×7 连续采集** 4 通道音频
- 内存里维持一个固定时长的 **环形缓冲** (BufferPool)，存最近 N 秒
- 算法侧用 HTTP/JSON 接口按 `[startTime, endTime]` 索要任意窗口的音频，秒级返回 WAV 字节
- 算法迭代不需要碰硬件，只需要改自己那段的取数窗口

## 典型工作流

```
[现场设备发声]
    ↓ (麦克风阵列 4 通道实时采集)
[net_audio 盒子]
    ├─→ 内存 BufferPool（最近 N 秒，按 channel 切片）
    ├─→ RingBuffer 落盘（recordings.narb，故障回溯）
    └─→ WebSocket stream（可选，给监控大屏实时显示波形/dBA）

[上游算法 / PLC / SCADA]
    ↓ 触发 detect 事件（"刚才那一下声音是什么？"）
[POST /api/v1/stop_and_fetch] —— 带 detectStageID + 时间窗 + 通道
    ↓ (盒子从 BufferPool 切片 + 转 WAV)
[返回 audio/wav 字节流] —— 单通道是裸 WAV，多通道是 multipart
    ↓
[上游算法做声学分析 / 模型推理]
```

## 跟"普通录音"的本质差异

| 维度 | 消费级录音 / 监控录音 | net_audio |
|---|---|---|
| 采集目标 | 完整音轨，可听 | 算法切片，可机读 |
| 时间精度 | "知道事情大概发生了" | 毫秒级时间窗口可索取 |
| 存储模型 | 文件按事件切分 | 内存环形 + 磁盘环形，固定容量覆盖 |
| 多机协同 | 各自录各自的，事后对齐 | 客户端 → 盒子时间同步协议，所有客户端拿到的时间轴一致 |
| 接入方式 | 文件下载 / RTSP 流 | HTTP/JSON + WebSocket + mDNS 自动发现 |
| 部署形态 | 独立设备 + 配套 NVR | 嵌入式盒子，多盒子产线集群 + 中心算法 |
| 鉴权模型 | 通常账号密码 | 算法直调路径**当前无鉴权**（产品决策：现场调用便利性优先；详见 [reference/10-deployment-modes.md](./10-deployment-modes.md)）|

## 跟"边缘智能盒子"的差异

net_audio **不做声学推理**。它的设计哲学是 **"采集与算法解耦"**：

- 算法在哪：上游（PLC / 中心服务器 / 算法节点）
- 模型版本：算法侧自己管
- 盒子升级频率：低（季度级别）
- 算法升级频率：高（周级别）

这套分工的代价是必须有"算法能精准索取音频"的接口 —— 也就是核心 API `/api/v1/stop_and_fetch`。详见 [reference/11-ai-integration.md](./11-ai-integration.md)。

## 产品形态

当前形态：**硬件 + 软件一体**，交付方式是预装了 SmartAudio 的 Rock Pi S 盒子（带麦克风阵列板），客户拿到接通电源 + 网线即可。详细部署模式见 [reference/10-deployment-modes.md](./10-deployment-modes.md)，商业模式框架见 [reference/07-pricing-business-model.md](./07-pricing-business-model.md)。

## 不适合的场景

为了节省双方时间，下列场景**不建议用 net_audio**：

- **要做高保真母带级录音**：本系统采样率默认 44.1kHz / 16bit，不是音乐级。
- **要做语音转写 / 会议记录**：上游可以用我们的 WAV 字节做 ASR，但 net_audio 自身不带 STT。
- **客户没有上游算法**：本系统不提供"现成的异常检测模型"，它是音频前端，配什么算法是客户的事。
- **要无人值守、零运维**：现场盒子需要时钟同步、灵敏度调校、网络配置等运维动作；详见 [scenarios/01-field-deployment.md](../scenarios/01-field-deployment.md)。
